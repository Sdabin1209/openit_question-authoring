# ADR 0023: 컴포넌트·스키마·연결로 나눈 영역 구조 (D117)

## 상태
채택(2026-10-30). 헤드 설계 `head/docs/DESIGN.md`(D117)를 따른다.

## 맥락
이전 구조는 `service.py`(489줄)가 권한, 초안 상태, 확인 규칙, 저장 순서를 한 클래스에 가졌고, 입력 검사가 `if`/`raise`로 코드 곳곳에 흩어져 있었다. 구조 규칙 6개(D104)는 컴포넌트가 자기 입출력 스키마와 업무밖에 모르기를 요구한다.

## 결정
- 일을 업무 단계로 나눠 컴포넌트 23개(`docs/components.md`)로 하고, 컴포넌트마다 입력·출력 JSON Schema(`schemas/`)를 둔다. 영역 사이 타입은 복사하지 않고 `$ref`로 계약을 가리킨다.
- 컴포넌트는 `run(입력) -> 출력` 함수다. 시각·새 ID·저장소 읽기 결과는 wiring이 입력으로 넘긴다(같은 입력, 같은 출력).
- 입력 검증과 출력 검증은 `wiring/schemas.py`의 `bind`가 한다. 컴포넌트에는 손 검사를 두지 않는다. 스키마로 쓸 수 없는 조건은 `schemas/README.md` 표에 이유와 함께 적는다.
- 저장소는 백엔드(메모리·SQLite·PostgreSQL) 컴포넌트와 읽기 논리 컴포넌트(`question_store`)로 나누고, 컴포넌트끼리 import할 수 없으므로 상속 대신 합성으로 wiring이 주입한다.
- HTTP 받는 쪽은 `openit_link.App`(D118) 위에 `link_authoring_server`로, 보내는 쪽은 `link_failures_read`로 둔다.

## 왜
- functional core, imperative shell(Bernhardt)과 포트·어댑터(Cockburn): 업무 규칙을 부수 효과 밖에 두면 입력만으로 시험된다(DESIGN 2절).
- 스키마가 입력 조건의 정본이면 문서·시험·검증이 어긋나지 않는다.
- 측정하지 않았다: 컴포넌트마다 입출력을 스키마로 검증하는 비용은 전체 시험 시간(약 2분)에서 눈에 띄는 차이를 보지 못했으나 별도로 재지 않았다.

## 검토한 대안과 버리는 이유
- 컴포넌트가 스스로 검증: 컴포넌트가 검증기 구현(레지스트리)을 알게 된다. 버린다.
- 상속으로 저장소 공유: 컴포넌트 사이 import가 생긴다. 버린다.
- 412·409 거부를 모두 스키마로: 이 거부는 저장된 상태에 대한 판정이라 입력 모양 조건이 아니다. 컴포넌트에 두고 `schemas/README.md` 표에 행마다 판정 이유를 적는다.
- `/v1/materials`를 link의 `stream_body`로: 환자 정보 점검, 해시, 추출, 원본 보관이 모두 본문 전체를 필요로 하고 상한이 8MiB(ADR 0016)라 메모리에 올리지 않을 이유가 없다. `raw_body` + `max_body`를 유지한다. 본문이 수 GiB가 되면 다시 본다.

## 결과
얻는 것: 업무 규칙을 서비스 없이 시험, 입출력이 스키마로 문서화. 감수하는 것: 호출마다 검증 비용, 컴포넌트 23개, 입력이 `Actor.id` 형식 오류면 역할 오류보다 먼저 INVALID_RECORD로 나온다(둘 다 틀린 호출만).

## 되돌리는 조건
검증 비용이 요청 지연에서 문제로 측정되면 출력 검증을 개발·시험에서만 켠다(R7이 허용하는 범위에서).
