# ADR 0015: 인증 실패는 401 + WWW-Authenticate, 권한 없음은 403

- 상태: 채택(2026-10-29, 계약 CONVENTIONS.md 6절, D106). 이 서비스의 "401이 아니라 403" 규약(boundary.md F7)을 대체한다
- 날짜: 2026-10-29

## 맥락
이 서비스는 토큰이 없거나 틀려도, 읽기 토큰으로 저작 경로를 불러도 모두 403을 냈다. 계약이 영역 사이 서비스 API(I1~I9)에 공개 API와 같은 구분을 요구한다.

## 결정
토큰이 없거나 틀리면(Bearer 형식이 아닌 것 포함) 401과 `WWW-Authenticate: Bearer`. 토큰은 맞지만 권한이 없으면 403(읽기 토큰으로 저작 경로, 저자 역할이 아닌 토큰, gateway 경유에서 아는 토큰이지만 모르는 사용자). gateway 토큰인데 `X-Openit-User`가 없으면 401(사람 행위자 신원 없음). `/healthz`·`/readyz`는 인증 없음. 본문 `code`는 둘 다 `PERMISSION_DENIED`, `retryable=false`. 본문을 읽기 전의 빠른 거절도 같은 규칙이다.

## 왜 (따른 표준과 근거)
RFC 9110 15.5.2(401은 요청에 유효한 인증 자격이 없음, 403은 이해했으나 수행을 거부)와 11.6.1(401은 도전을 담아야 함), RFC 6750 3절(Bearer 도전). 계약이 이를 정했다(원문 대조는 하지 않았고 계약 문구를 따랐다).

## 검토한 대안과 버리는 이유
- 현행(모두 403) 유지: 계약과 어긋난다.
- gateway에서 모르는 사용자도 401: 신원은 제시됐으나 이 서비스에 권한이 없는 경우라 403으로 했다. 형식이 틀린 사용자 ID도 같다(계약이 이 경우를 명시하지 않아 이 영역의 해석이다. 헤드 확인 필요).
- I7(ops-feedback)이 우리 호출을 거절한 경우: 호출한 저자의 인증이 아니라 상류 장애라 이전과 같이 403을 유지했다(계약이 말하지 않은 부분, 이 영역의 해석).

## 결과
얻는 것: 계약 준수, `boundary_contracts.clients`는 401·403을 모두 `PERMISSION_DENIED`로 읽어 클라이언트 변경 없음. 감수하는 것: 기존 403 기대 시험을 고쳐야 했다.

## 되돌리는 조건
계약이 바뀌면 따른다.
