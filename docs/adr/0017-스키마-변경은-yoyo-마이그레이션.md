# ADR 0017: 스키마 변경은 yoyo-migrations

- 상태: 채택 (2026-10-29, D111). ADR 0001의 "시작 때 `CREATE IF NOT EXISTS` + `schema_version` 표지 + 코드 안 `ALTER TABLE`" 방식을 대체한다(표준성 점검 #23: 마이그레이션 이력 없음).
- 날짜: 2026-10-29

## 맥락
스키마를 시작 때마다 멱등 DDL로 만들고, 열이 늘면(`blobs.created_at`, D88 U4) 코드 안에서 `PRAGMA table_info`로 확인해 `ALTER TABLE`을 했다. 어떤 DB가 어느 모양인지 기록이 없고, 새 버전이 만든 DB를 옛 코드가 읽는지 막을 수 없었다. 표준 관행은 버전이 붙은 마이그레이션 도구다.

## 결정
yoyo-migrations 9.0.0. 마이그레이션 파일은 `question_authoring/migrations/{sqlite,postgres}/NNNN.이름.py`(방언별 디렉터리, 각 파일은 `step()`의 연속)이고 이력 표는 `qa_migration`이다. 시작 때 `store/migrate.py`가 적용한다. 읽기 전용 연결은 적용하지 않고 `qa_migration`이 코드가 아는 목록과 정확히 같을 때만 연다.

## 왜 (근거)
- 이력이 DB 안에 남고(어느 DB가 어디까지 왔는지), 적용 순서와 의존(`__depends__`)이 명시된다.
- 여러 인스턴스가 동시에 시작해도 yoyo의 잠금 테이블이 직렬화한다(이전에는 PostgreSQL advisory lock을 직접 썼다). 잠금 대기 30초는 측정 안 한 여유값이다.
- 선택 이유: SQLite와 PostgreSQL을 둘 다 지원하고 SQL 직접 작성이 가능하며 의존이 작다(sqlparse, tabulate). 같은 단위의 다른 영역과 도구를 맞춘다(D111).
- `.py` 마이그레이션 + `step(문자열)`: `.sql` 파일은 yoyo가 문장을 나누는데, SQLite `CREATE TRIGGER ... BEGIN ... END`와 PostgreSQL `$$` 함수 본문에서 잘못 나눌 위험을 피한다. `.py`의 문자열 step은 나누지 않고 한 문장으로 실행한다.
- 도입 이전 DB를 그대로 받는다: 0001은 `IF NOT EXISTS`/`OR REPLACE`/`DROP TRIGGER IF EXISTS`라 이미 있는 스키마에서 시작해도 된다. `blobs.created_at`(옛 DB에는 없을 수 있음)은 0002가 있을 때 건너뛴다. 시험: `tests/test_migrations.py`(열이 있는/없는 옛 SQLite DB, 옛 PostgreSQL DB).

## 검토한 대안과 버리는 이유
- Alembic: SQLAlchemy 모델 위주 도구라 이 영역(SQLAlchemy 없음, SQL 직접)에는 의존이 커진다.
- 현상 유지(IF NOT EXISTS + 표지): 이력이 없고 미래 DB 거부가 `schema_version` 문자열 하나뿐이다.

## 결과
- 얻는 것: 이력, 동시 시작 안전, 미래 DB 거부(적용된 마이그레이션이 코드가 아는 것과 다르면 `UNAVAILABLE`, `/readyz` 503).
- 감수하는 것: `meta` 표(옛 DB에 남아 있다, 새 DB에는 만들지 않는다). 새 열을 늘릴 때마다 마이그레이션 파일을 더한다. 되돌리기(rollback) 마이그레이션은 쓰지 않는다(불변 레코드 저장소라 데이터를 지우는 방향은 두지 않는다).
- SQLite 인메모리 시험 DB(`path=None`)는 닫을 때 지우는 임시 파일이 된다: yoyo가 별도 연결로 적용하는데 `:memory:`는 연결마다 다른 DB다.

## 되돌리는 조건
SQLAlchemy를 도입하거나 yoyo 유지가 멈추면 Alembic을 검토하고 이 ADR을 대체한다.
