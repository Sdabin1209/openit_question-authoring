# ADR 0004: 문항 자료 파싱은 직접 쓴 선형 줄 파서

- 상태: 채택(0.1.0), 선형화는 0.6.3
- 날짜: 2026-10-28

## 맥락
저자(의료인)가 올린 문항 자료를 문항 초안으로 바꿔야 한다(D31, D33). 확신하지 못한 값은 추정하지 않고 알려야 한다(brief 4절). 점검(P1)이 정규식과 목록 탐색이 제곱 시간임을 실측했다: 160,000자 공백 한 줄에 62.9초, 슬롯 16,000줄에 26초, 문항 10,000줄에 44초. 요청 하나가 GIL을 쥔 채 서비스를 멈출 수 있었다.

## 결정
형식마다 추출기(`extractors/`)를 붙이는 구조(D33)와, 첫 추출기로 규칙 기반 '텍스트 양식'(`text-form`, 줄 문법). 줄은 `str.find`로 첫 콜론에서 나누고(`_KV` 정규식 제거), 플래그 중복 검사는 집합으로 한다. 정규식에 남는 모양 검사는 값 한 줄 안에서만 쓰고 줄 길이를 4096자로 묶었다. 상한: 줄 4096자, 문항 2000, 문항당 슬롯 200, 플래그 5000, 시간 예산 20초. 넘으면 추측하지 않고 `ExtractionFailure`(또는 해당 줄 UNPARSED) -> 화면 입력으로 이어 간다.

## 왜 (따른 표준과 근거)
- 규칙 기반인 이유(design.md 7.1, 제안): 결정적이고 시험할 수 있다, 모델·외부 라이브러리 불필요, 어느 줄을 해석하지 못했는지 정확히 알려 줄 수 있어 조용한 추정이 없다, 이후 PDF·Word 추출기가 텍스트 추출까지만 하고 이 파서를 재사용할 수 있다.
- 선형화의 근거: 점검의 실측과, 정규식의 되돌림(backtracking)이 입력 길이의 제곱이 되는 알려진 문제(ReDoS). 표준 대응은 되돌림이 없는 분할·선형 알고리즘과 입력 상한이다. 효과는 측정했다: 같은 입력이 모두 5초 안(시험 `tests/test_extractor_scale.py`, 8MiB 변형 포함 10초 안).
- 상한값(4096, 2000, 200, 5000, 20초)은 측정이나 표준에서 나온 값이 아니다: 정상 자료(문항 수십 개)의 수십~수백 배로 잡은 여유값이다. **근거 기록 없음(판단)**, 실제 저자 자료로 분포를 재지 않았다.
- 선행 조건 줄은 새 구현이 옛 정규식과 같은 결과를 내는지 무작위 입력으로 비교했다(`=`가 둘 이상인 병적 입력은 더 보수적으로 플래그).

## 검토한 대안과 버리는 이유
- 정규식 유지 + 안전한 엔진(re2): 의존이 늘고 되돌림이 아닌 구조로 바꾸는 것이 더 단순하다. 버림.
- 파싱 라이브러리/문법 생성기: 줄 문법이 단순하고 UNPARSED 보고가 핵심이라 직접 쓰는 편이 통제하기 쉽다고 판단(비교 안 함).
- LLM 파싱: 비결정적이고 임상 의미를 바꿀 수 있다(brief 7절, 확인 절차 필요). 버림.
- 자료 크기만 제한하고 정규식 유지: 8MiB 상한에서도 100KB 한 줄이 분 단위. 버림.

## 결과
얻는 것: 입력 크기에 선형, 정상 파싱 결과 동일(회귀 시험). 감수하는 것: 매우 큰 정상 자료는 FALLBACK으로 간다(2000 문항 초과 등). 추출은 요청 스레드에서 동기 실행되며 시간 예산은 협조적(줄 256개마다 확인)이다. 한 줄 안의 정규식은 4096자 이하라 한정되지만 완전한 시간 보증은 아니다.

## 되돌리는 조건
실제 저자가 한도를 넘는 정상 자료를 올리면 한도를 올린다. 프로세스 격리(추출 전용 워커)는 PDF·Word 추출기를 붙일 때 다시 검토한다.
