# ADR 0025: 사람용 요청마다 서버 쪽 요청 전체 마감 (D120)

## 상태
채택(2026-10-31). 헤드 결정 D120을 따른다. 이 영역의 시간 시험 기준은 [ADR 0024](0024-시계는-주입한다.md).

## 맥락
gateway는 응답 머리글을 기다리는 상한이 있다(저작 경로 13초, deploy ADR 0048의 시간 사슬, D119). U427 점검에서 이 영역의 서버 쪽 최악이 그보다 길었다: PostgreSQL 운영 구성에서 큰 자료 쓰기 문장 하나가 31초(상한 30초 + 감시 1초), 자료 올리기는 원본·초안 두 번이라 62초. 그러면 서버는 계속 일하는데 화면은 504를 받는다.

## 결정
- 사람용(gateway를 지나는) 요청마다 서버 쪽 **요청 전체 마감**을 둔다. 기본 12.0초, 환경 변수 `QA_REQUEST_DEADLINE_SECONDS`(0 초과 600 이하)로 바꾼다.
- 마감은 요청 시작 때 정하고 컨텍스트 변수에 둔다(`wiring/deadline.py`의 `RequestDeadline`). 시계는 주입한다(ADR 0024): 진입점이 `time.monotonic`을 넣는다.
- 각 DB 문장은 남은 시간을 상한으로 쓴다. 남은 시간이 고정 상한(문장 3초, 큰 자료 30초 + 감시 1초)보다 짧으면 남은 시간이다: 감시 타이머의 시한과 쓰기 트랜잭션의 서버 쪽 `SET LOCAL statement_timeout`이 `min(고정 상한, 남은 시간)`을 받는다. 남은 시간이 0 이하이면 연결도 문장도 시작하지 않는다.
- 서비스는 쓰기 직전마다(초안 저장, 원본 자료 저장, 번호 예약, 버전 저장, 검수 저장) 마감을 확인하고, 넘겼으면 저장하지 않고 503 `UNAVAILABLE`(retryable=true)을 낸다. 감시 타이머가 닫은 연결의 트랜잭션은 서버가 되돌린다(반쯤 쓴 상태 없음).
- 같은 요청을 다시 보내도 안전하다: 원본 자료는 내용 해시 키(`ON CONFLICT DO NOTHING`), 확인은 예약한 버전 번호와 같은 해시 멱등, 검수는 `review_id` 멱등(기존 장치, ADR 0004·0011). 새 멱등 키는 만들지 않았다.
- 버전 저장이 끝난 뒤의 마무리 기록(초안 상태를 CONFIRMED로)은 마감을 확인하지 않는다: 버전은 이미 저장됐고 다시 보내도 멱등이다.

## 왜
- 마감 전파(deadline propagation, gRPC deadline과 같은 생각): 바깥(화면 > gateway)의 시한이 안쪽(서버 > DB) 시한을 정한다. 12초는 gateway 응답 머리글 상한 13초 − 여유 1초이고, 정상 요청은 이 PC 실측으로 훨씬 안이다(8MiB 삽입 0.09초, ADR 0003·0007; 한 요청 전체는 측정하지 않았다).
- 컨텍스트 변수: 처리 스레드마다 따로 이어지고, 서비스·저장소 메서드 시그니처를 모두 바꾸지 않는다.

## 검토한 대안과 버리는 이유
- 고정 상한만 줄이기(큰 자료 30초 → 10초): 요청 하나의 문장 수와 무관하게 합이 마감을 넘을 수 있다. 버린다.
- 모든 메서드에 마감 인자 추가: 변경이 크고 빠뜨리기 쉽다. 컨텍스트 변수로 한 곳에서 시작한다.
- 기본값을 gateway 상한과 같게(13초): 서버가 응답을 내보낼 시간이 없다. 여유 1초를 둔다.

## 결과
얻는 것: 노출 선언(response_header 13초)과 서버 쪽 최악이 맞는다(`tests/test_exposure_timeouts.py`가 설정 값끼리 비교). 감수하는 것: 느린 환경에서 큰 자료가 마감에 걸리면 503이 되고 다시 보내야 한다(운영 PostgreSQL에서 12초 안에 못 끝나는 8MiB는 측정하지 않았다). 잡(purge 등)은 요청 범위 밖이라 마감이 없다.

## 되돌리는 조건
정상 요청이 마감에 걸린다는 운영 신호가 있으면 gateway 상한과 함께 사슬을 다시 정한다(헤드).
