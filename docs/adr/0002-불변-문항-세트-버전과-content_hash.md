# ADR 0002: 불변 문항 세트 버전과 content_hash

- 상태: 채택(D25, 2026-10-14 설계)
- 날짜: 2026-10-28

## 맥락
게이트·합성 데이터·모델 학습이 '정확히 이 문항 세트'를 가리켜야 한다. 문항을 고치면서 이미 평가·학습에 쓴 버전이 바뀌면 재현이 깨진다.

## 결정
문항 세트 버전은 한 번 쓰면 바꾸지 않는다. 수정은 새 버전(번호 +1)이다. 참조는 `ArtifactRef(id, version, content_hash)`이고 `content_hash`는 `boundary_contracts.canonical.sha256_hash(QuestionBank)`다. 읽을 때마다 해시를 다시 계산해 저장된 값·ref와 다르면 `INTEGRITY_ERROR`. 저장소는 `versions`, `reviews`, `changes`에 UPDATE/DELETE 트리거를 둔다.

## 왜 (따른 표준과 근거)
- 경계 계약의 레코드는 모두 불변(D25, `head/docs/DECISIONS.md`). 이름·버전·내용 해시로 가리키는 것이 계약의 `ArtifactRef` 규약이다(브리프 '버전' 절).
- 해시를 읽을 때 재계산하는 이유: DB에서 내용이 몰래 바뀌어도(백업 복원 실수, 직접 수정) 잘못된 문항이 게이트로 나가지 않게 한다. 표준 관행(내용 주소 지정, git·컨테이너 digest와 같은 원리).
- `QuestionBank.version`(정수)을 버전 번호와 같게 한 것은 CR-0002에서 헤드가 승인했다.
- 검수는 별도 `ReviewRecord`로 덧붙이고 이전 것을 지우지 않는다: 승인 철회도 기록으로 남아야 하기 때문(design.md 5.3).

## 검토한 대안과 버리는 이유
- 제자리 수정 + 변경 이력 테이블: 이미 쓴 버전의 내용이 바뀔 수 있어 재현이 깨진다. 버림.
- 해시 없이 번호만: 같은 번호에 다른 내용을 막을 수 없다. 버림.
- 해시 알고리즘을 직접 고르기: 계약 패키지의 `canonical`이 정한 것을 쓴다(독자 규약을 만들지 않는다).

## 결과
얻는 것: 재현성, 변조 탐지, 멱등 재전송(같은 번호·같은 해시는 OK, 다른 해시는 CONFLICT). 감수하는 것: 오타 하나도 새 버전이고, 저장 공간이 버전 수만큼 는다(문항 세트는 작아 문제로 측정된 적 없음, 측정 안 함). 읽기마다 해시 계산 비용(측정 안 함).

## 되돌리는 조건
계약(D25)이 바뀌어 가변 레코드를 허용할 때만. 그럴 일이 아니라면 되돌리지 않는다.
