# ADR 0009: 개선 신호 I7 읽기를 이 영역이 한다

- 상태: 채택(0.4.0, D52), 필드 수정은 0.6.3(M-6)
- 날짜: 2026-10-28

## 맥락
실패 사례(ops-feedback)에서 어떤 문항이 자주 틀리는지는 문항을 고칠 저자에게 가장 쓸모 있다. 문항을 소유하는 영역이 이 영역이다(brief 3절, 소비하는 계약 FailureCase).

## 결정
ops-feedback의 읽기 SDK(`HttpFailureStore`)로 실패 사례와 비식별 trace를 읽어 문항별 건수·유형 분포·혼동·CONFIRMED 수만 계산해 `GET /v1/signals`로 낸다(읽기 전용, 저장 안 함, 발화 문장 제외). 문항 ID는 v2 TurnTrace의 `extract_input.question_id`에서 읽는다(v1 `planner_output.directive`는 옛 trace용으로 남김).

## 왜 (따른 표준과 근거)
- 영역 경계 규칙: 이웃의 데이터는 그 영역이 배포한 읽기 SDK/HTTP로만 읽는다(워크스페이스 CLAUDE.md). 문항 수정의 결정권이 저자에게 있고(brief) 자동 수정은 하지 않는다.
- 발화를 저장하지 않는 이유: O19(비식별 뒤 발화 보존 범위, 잠정 B)가 미정이라 구조 정보만 쓴다.
- v2 필드로 바꾼 이유: 전수 점검 횡단 M-6이 v1 필드만 읽어 v2에서 문항 단위 신호가 항상 비는 것을 지적했다. `extract_input.question_id`는 TurnTrace 스키마에서 필수인 필드다(`ExtractionInputRecord.required`).
- 상류 장애는 건너뛰지 않고 실패(FAULT_POLICY 10).

## 검토한 대안과 버리는 이유
- 신호를 ops-feedback이 계산: 문항 단위 해석은 문항 소유 영역 관심사이고 ops-feedback은 사례 수집이 일이다. 다만 경계 합의 기록은 없다(근거 기록 없음, 구조 분담은 D52 전후 설계에서 정해짐).
- 신호를 저장: 읽을 때 계산하면 저장·보존 문제가 없다.

## 결과
얻는 것: 저자가 보는 문항별 신호. 감수하는 것: 읽을 때마다 상류를 부른다(총 마감 20초). `question_id`가 슬롯 키 형태일 가능성은 ops-feedback과 확인하지 못했다.

## 되돌리는 조건
ops-feedback이 문항 단위 집계를 직접 제공하면 그것을 읽도록 바꾼다.
