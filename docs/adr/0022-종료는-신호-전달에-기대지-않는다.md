# ADR 0022: 우아한 종료는 SIGINT 전달에 기대지 않는다

- 상태: 채택 (2026-10-30, U308). ADR 0016의 종료 절차 한 줄을 고친다.

## 맥락
전체 E2E 안의 check-all에서만 `python -m question_authoring`이 SIGTERM에 10초 안에 끝나지 않았다(시험 2개 실패, 혼자·병렬·E2E 밖 check-all은 통과). 서버는 SIGTERM 처리기에서 진행 중 요청을 기다린 뒤 `signal.raise_signal(SIGINT)`로 주 스레드의 `srv.run()`을 끝냈다.

## 원인 (확인한 것)
POSIX: 비대화형 셸이 `&`로 띄운 작업은 SIGINT·SIGQUIT를 **무시(SIG_IGN)로 시작**하고, Python은 시작 때 SIGINT가 이미 무시이면 기본 처리기(`KeyboardInterrupt`)를 설치하지 않는다. E2E 하네스는 서버를 이런 배경 작업 아래에서 띄운다. 재현: 비대화형 `bash -c '서버 & ...'`로 띄운 프로세스의 `/proc/<pid>/status`가 `SigIgn: 0000000001001006`(SIGINT=0x2 포함)이고, SIGTERM 뒤 12초가 지나도 안 끝났다. `raise_signal(SIGINT)`가 아무 일도 하지 않았기 때문이다. 시험으로 고정: `tests/test_ops_hardening.py::test_sigterm_stops_the_server_even_when_signals_were_inherited_as_ignored`(수정 전 SIGINT 무시 두 경우 실패, 수정 후 통과). 헤드가 시도한 setsid·nohup·stdin 분리는 SIGINT 상속에 영향이 없다.

## 결정
종료 신호가 아니라 waitress의 트리거(`srv.trigger.pull_trigger`)로 서버 루프 스레드 안에서 모든 소켓을 닫아(`close_all`) 이벤트 맵을 비운다. 맵이 비면 `srv.run()`이 스스로 돌아온다. 물려받은 신호 처리와 무관하다.

## 왜
- SIGTERM 처리기는 우리가 직접 설치하므로 상속된 상태에 영향받지 않는다. 그 뒤의 "주 루프를 깨우는 수단"도 상속된 신호 상태가 아니라 프로세스 안의 장치여야 한다.
- 트리거는 waitress가 다른 스레드에서 루프를 깨우는 공식 수단이다. 단 thunk의 예외를 삼키므로 `SystemExit`으로 끝낼 수 없다.

## 검토한 대안과 버리는 이유
- 시작 때 `signal.signal(SIGINT, default_int_handler)`로 상속된 무시를 덮어씀: 서버가 SIGINT를 받는 이유도 바뀌고(운영자가 의도한 무시를 덮음) 원인을 신호에 계속 의존한다.
- 시험의 `wait(timeout)`를 늘림: 서버가 영영 안 끝나는 것이라 효과가 없다.
- 다른 신호(SIGUSR1) 처리기를 따로 설치: 신호 의존이 남는다.

## 결과
- 얻는 것: SIGTERM 뒤 0.1초에 종료(위 재현에서). 유예 시간 초과 때의 `os._exit(0)` 경로는 그대로다.
- 감수하는 것: `srv._map`(waitress 내부 속성)을 `close_all`과 `drain`이 읽는다. waitress 버전을 올릴 때 시험(`tests/test_server_properties.py`, 위 시험)이 먼저 깨진다.
