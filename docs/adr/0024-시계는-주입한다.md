# ADR 0024: 컴포넌트는 시간을 직접 읽지 않고 시계를 주입받는다 (U422)

## 상태
채택(2026-10-31).

## 맥락
시험이 실제 시간을 기다리거나 재서 합격·불합격을 정하면 기계가 바쁜 정도에 따라 결과가 바뀐다(실패해도 결함이 아니고 통과해도 옳다는 뜻이 아니다). 이 영역의 시간 시험은 세 종류였다: 우리가 정한 마감(추출 시간 예산, 개선 신호 읽기의 총 마감, 종료 때 유예), 라이브러리 동작(waitress 연결 시한, PostgreSQL statement_timeout, psycopg 접속 시한, docker pause, SIGTERM), 속도 측정(`took < N`).

## 결정
- **우리 코드의 시간**은 컴포넌트가 직접 읽지 않고 인자로 받는다: `extract_textform.run(inp, clock=)`와 `TextFormExtractor(clock)`, `FailureReader(source, clock=)`, `drain(srv, grace, clock=, sleep=)`, 저장소 백엔드의 `now_ts=`, PostgreSQL 백엔드의 `timer=`(시한이 지나면 함수를 부르는 타이머)·`wait=`(이벤트를 최대 N초 기다리는 함수), `signals_build.build_signals(now=)`. 실제 시계는 wiring(`wiring/service.py`, `wiring/stores.py`)과 진입점(`__main__.py`)이 넣는다. 시험은 가짜 시계·즉시 시한이 지난 타이머를 넣어 시간을 직접 흘린다.
- **라이브러리 안의 시간**은 시험하지 않는다. (a) 라이브러리에 넘기는 값(waitress `channel_timeout`·`threads`·`max_request_body_size`, 접속 인자의 `connect_timeout`·`statement_timeout`)을 확인하고 (b) 가짜 의존이 즉시 시간 초과 예외를 던질 때의 우리 결과(UNAVAILABLE, 재시도 여부, 비밀 비노출)를 확인한다.
- **속도 측정**은 시험에서 뺀다. 정규식·추출기의 제곱 시간 방어는 "큰 입력이 끝난다"만 보고(`run_bounded`), 끝나지 않는 결함은 매달림 감시(`HANG_GUARD_SECONDS`=300)에 걸리게 한다.
- 시험이 자기 가짜에게서 신호를 기다리는 대기는 판정이 아니라 매달림 감시이고 숫자는 `tests/helpers.py`의 상수 하나(근거 주석 포함)만 쓴다.

## 왜
- 표준 관행: 의존성 주입으로 시계·타이머를 바깥에서 받는 것(Seemann, 『Dependency Injection』의 Ambient Context 대안 비판), functional core / imperative shell(DESIGN 2절)과 같은 방향이다.
- 같은 입력이면 같은 출력(DESIGN 2절)이려면 시간이 입력이어야 한다.

## 검토한 대안과 버리는 이유
- 전역 time 패치(freezegun 등): 블로킹 대기(`Event.wait(timeout)`, 소켓 timeout, `threading.Timer`)는 움직이지 못하고, 어느 모듈이 어떤 시계를 쓰는지 숨는다.
- 상한을 늘려 시험을 덜 깨지게 하기(U420): 부하가 충분히 크면 여전히 깨지고, 위쪽 상한 단언은 결과가 아니라 속도를 시험한다.
- 실제 서버·DB로 시한을 재는 시험을 영역 시험에 두기: 라이브러리를 시험하는 일이고 기계에 달린다. smoke·E2E의 몫이다(`tests/TIMING.md`에 지운 시험 목록).

## 결과
얻는 것: 영역 시험의 합격·불합격이 기계 부하와 무관하다. 감수하는 것: 시계를 받는 인자가 늘었다(컴포넌트 시그니처 6곳). 와이어 형식·HTTP 응답·잡 출력은 그대로다(시험: 전체 영역 시험의 계약·HTTP 시험이 변경 전과 같은 기대값으로 통과).

## 되돌리는 조건
없다(시험의 결정성은 되돌릴 이유가 없다). 시계 인자가 지나치게 퍼지면 작은 `Clock` 객체 하나로 묶는다.
