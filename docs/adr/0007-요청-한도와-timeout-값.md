# ADR 0007: 요청 한도와 timeout 값

- 상태: 채택(0.6.1~0.6.3), 값은 잠정 기본값
- 날짜: 2026-10-28

## 맥락
FAULT_POLICY 원칙 4: 의존이 응답하지 않을 때 무한히 기다리지 않는다. 기본값과 근거를 영역 문서에 적는다. 전수 점검은 본문 8MiB, 스레드 무제한, 인증 전 본문 수신을 지적했다.

## 결정
설정으로 바꿀 수 있는 기본값: DB 접속 3초, 문장 3초(서버 `statement_timeout`; 얼어붙은 서버는 +1초 뒤 클라이언트가 소켓을 닫음), `/readyz` 2초, 큰 자료 쓰기 문장 30초, 요청 소켓 무응답 30초, 동시 요청 32, I7 호출 5초·총 마감 20초, 본문 8MiB, 추출 시간 20초.

## 왜 (따른 표준과 근거)
- 문장 3초/접속 3초: 정상일 때 문장은 수 ms이고(이 PC에서 8MiB 삽입도 0.09초) 쓰기 하나는 몇 문장이라 3초면 느린 디스크·잠깐의 락 대기는 견딘다. 이웃(게이트)의 호출 대기보다 짧게 둔다[제안, 측정은 이 PC 한 환경]. libpq는 접속 timeout을 정수 초로 보고 2초 미만을 2초로 본다(psycopg/libpq 문서).
- `/readyz` 2초: FAULT_POLICY 원칙 5가 '2초 안에 503'이라 정했다. 로드 밸런서 검사 제한이 보통 수 초라는 일반 관행과 맞는다.
- 큰 자료 30초: 8MiB 삽입을 한 환경에서 0.09초로 쟀으나 실제 디스크·네트워크 DB에서의 값은 측정 안 함. 정상 업로드가 UNAVAILABLE로 실패하는 것이 더 나쁘므로 약 300배 여유를 둔 값이다. **근거 기록 없음(여유값)**.
- 요청 소켓 30초: 느린 링크에서 8MiB를 보낼 시간을 고려한 값이나 **근거 기록 없음, 측정 안 함**. 읽기/쓰기 소켓이 이 시간 멈추면 끊어 스레드를 놓게 한다.
- 본문 8MiB(`MAX_BODY`): 도입 시 근거 기록 없음(git log·design.md에 이유가 없다). 문항 자료는 텍스트 양식이라 작고, 이 값은 메모리 상한(동시 32 x 8MiB = 256MiB)을 계산 가능하게 하는 선이다. 실제 자료 분포는 모른다.
- 동시 32: 사용자가 관리자 소수라는 가정의 넉넉한 값, 측정 안 함. 넘으면 503 + Retry-After. `/healthz`·`/readyz`는 세지 않는다. 인증 헤더가 없거나 모르는 토큰이면 본문을 읽지 않고 403.
- I7 5초/20초: 호출 하나가 10초(클라이언트 기본)이던 것을 줄였다. 목록·trace를 여러 번 부르는 한 요청의 총 마감을 둔 것은 FAULT_POLICY 4·10에 따른 것이고 값은 **근거 기록 없음(여유값)**.

## 검토한 대안과 버리는 이유
- 한도 없음: 점검이 무한 대기·자원 고갈을 실측으로 보였다. 버림.
- 프레임워크의 기본값 사용: 서버가 표준 라이브러리 `ThreadingHTTPServer`(ADR 0012)라 기본 제한이 없다.

## 결과
얻는 것: 모든 대기가 유한하고 설정 가능. 감수하는 것: 값 대부분이 잠정이다. 컨테이너 조합 재측정은 deploy E2E에서 헤드가 한다.

## 되돌리는 조건
실제 운영 측정으로 값이 틀렸다고 드러나면 설정으로 바꾸고 이 ADR을 대체한다.
