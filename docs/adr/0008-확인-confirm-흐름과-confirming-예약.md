# ADR 0008: 확인 confirm 흐름과 confirming 예약

- 상태: 채택(0.1.0), 예약 해제는 0.6.3(A7)
- 날짜: 2026-10-28

## 맥락
확인은 여러 단계(미리보기 해시 대조, 열린 플래그 0, 기반 최신 여부, 번호 부여, 스키마 검증, 변경 분류, 한 트랜잭션 저장, 초안 상태 갱신)이고 중간에 프로세스가 죽거나 응답을 잃을 수 있다. 저자는 같은 요청을 다시 보낼 수 있어야 한다.

## 결정
초안(OPEN) -> 미리보기(해시) -> `confirm(preview_hash)`. 처음 시도에서 버전 번호와 시각을 초안의 `confirming`에 **예약**하고 저장한 뒤 같은 값으로 커밋한다. 재시도는 같은 번호·시각으로 같은 레코드를 만든다. 같은 해시의 재확인은 같은 ref(멱등), 다른 해시는 CONFLICT. 다른 초안이 같은 번호를 먼저 가져가 커밋이 CONFLICT가 나면 예약을 풀고 FAILED_PRECONDITION으로 처음부터 다시 시작하게 한다.

## 왜 (따른 표준과 근거)
- 예약의 이유: 커밋은 됐는데 응답/초안 갱신을 잃은 경우에도 재시도가 중복 버전을 만들지 않고 같은 레코드를 얻게 하려는 것이다(멱등 키를 서버에 두는 표준 기법). 시험: `test_fault_paths`, `test_two_person`.
- 미리보기 해시를 요구하는 이유: 저자가 **본 것**과 확정되는 것이 같음을 보장한다(D31, 파싱 결과는 확인 전에는 버전이 아니다).
- 예약 해제: 점검 A7이 예약된 번호가 다른 초안에 의해 소진되면 영영 CONFLICT가 반복되는 것을 지적했다.

## 검토한 대안과 버리는 이유
- 확인 때마다 번호를 새로 계산: 응답 유실 후 재시도가 두 번째 버전을 만들 수 있다. 버림.
- 클라이언트가 멱등 키 제공: 저자는 컴퓨터 전문가가 아니다(brief 1절). 서버에서 만든다.

## 결과
얻는 것: 중간 중단에도 한 번만 저장. 감수하는 것: 초안에 상태 필드가 하나 더 있고, 같은 내용의 다른 초안이 같은 번호로 확인되면 먼저 커밋된 버전과 해시가 같을 때 조용히 성공하며 그 초안의 검수 기록은 따로 남지 않는다(알려진 한계). 초안 동시 편집은 프로세스 안 잠금으로 직렬화한다(단일 프로세스 전제).

## 되돌리는 조건
여러 프로세스로 확장하면 잠금 대신 저장소의 revision 비교 저장으로 바꾼다.
