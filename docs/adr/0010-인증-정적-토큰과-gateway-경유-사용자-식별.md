# ADR 0010: 인증 정적 토큰과 gateway 경유 사용자 식별

- 상태: 채택(정적 토큰 0.3.0, gateway 경로는 D88 E2 준비 0.6.3)
- 날짜: 2026-10-28

## 맥락
읽기 면(I1)과 저작 면은 서로 다른 권한이다. 운영에서 저자 클라이언트가 이 서비스에 닿게 할지는 사용자 결정(E2)이고 그 준비만 한다. 4-eyes(ADR 0006)는 사람 단위 식별이 필요하다.

## 결정
(a) 정적 Bearer 토큰 표(`QA_AUTHOR_TOKENS` `토큰:ID:역할`, `QA_READ_TOKENS` 읽기 전용). (b) gateway 경유: gateway가 사람 인증(Basic 등)을 마친 뒤 서비스 토큰(`QA_GATEWAY_TOKENS`)과 `X-Openit-User: <ID>`를 붙인다. 이 서비스는 gateway 토큰의 요청에서만 그 헤더를 믿고(정적 토큰의 요청에서는 무시), 사용자의 역할은 `QA_USER_ROLES` 표로 정한다. 모르는 사용자·헤더 없음은 403. 서비스 포트는 직접 노출하지 않는다.

## 왜 (따른 표준과 근거)
- `X-Openit-User` 규약은 boundary-contracts `HTTP.md`(승인자 식별)와 `PUBLIC_API.md`(직원 개별 계정)가 정한 것을 따른다: 게이트웨이가 인증하고 헤더를 붙이며 클라이언트가 보낸 같은 이름 헤더는 지운다. 본문 값은 믿지 않는다.
- 헤더를 gateway 토큰 보유자에게만 허용하는 이유: 서비스에 직접 닿을 수 있는 다른 호출자(같은 네트워크의 이웃)가 헤더를 위조해 신원을 사칭하지 못하게 하려는 것이다.
- 역할표를 서비스에 둔 이유: gateway가 역할까지 헤더로 보내는 규약이 없다(HTTP.md에 `X-Openit-User`뿐). 새 헤더는 계약 변경이라 만들지 않았다.
- 이메일형 ID는 계약 `Id`에 맞게 `@`를 `:at:`로 바꿔 기록한다(2차 점검: 이전에는 `_principal`과 `_ID`가 달라 400).
- 토큰 비교는 dict 조회(상수 시간 비교 아님): 점검 B10이 지적한 L 항목, 외부에 노출되지 않아 수정하지 않음.

## 검토한 대안과 버리는 이유
- 서비스가 자체 로그인/세션: 콘솔이 아직 없고 인증 인프라는 gateway 몫이다. 버림.
- JWT: 서명키·만료 관리가 새로 생긴다. 지금 규모에 이득이 작다(비교 안 함).
- 역할을 별도 헤더로: 계약 변경 필요. CR 없이 만들지 않음.

## 결과
얻는 것: gateway가 열리면 사용자 단위 식별로 4-eyes가 의미를 가진다. 감수하는 것: 토큰은 정적이고 회전하려면 재시작이 필요하다. 사용자 목록을 서비스 설정에 따로 관리한다. 시작 시 운영 구성(DB URL, 토큰)이 없으면 거부한다(`QA_DEV_MODE` 예외).

## 되돌리는 조건
gateway가 역할 헤더 규약을 계약에 넣으면 역할표를 지운다.
