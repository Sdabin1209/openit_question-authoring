# 영역 브리프: 문항 저작 (question-authoring)

> **계약 상태.** 영역 사이 계약은 `../boundary-contracts`(헤드 소유)에 있고, 이 브리프의 계약 이름은 `head/docs/STRUCTURE.md`의 제안이다. 초안이 있는 것은 ReleaseManifest, GateDecision, TraceEnvelope뿐이고 나머지 필드는 헤드가 사용자와 논의해 확정 중이다. 확정 전에는 **계약에 의존하지 않는 부분**(내부 설계, 도메인 모델, 테스트 틀)만 진행한다. 계약이 부족하다고 느끼면 임의로 가정하지 말고 `docs/change-requests/`에 쓴다.
> **읽기.** `../boundary-contracts`와 `../survey-service/schema`는 문진 서비스의 데이터 스키마(스키마만 남긴 최소 구성)다. 구현이 가져가는 계약은 `schemas/<계약명>.json`(JSON Schema Draft 2020-12), 컴포넌트별 입력·출력 대응은 `COMPONENTS.yaml`, 정수 버전은 `CONTRACT_VERSION`이다. 둘 다 읽기 전용이다.
> **버전(D14, D19).** 문진 스키마는 정수 버전(`CONTRACT_VERSION`, 현재 1)에 정확히 일치해야 한다. 경계 계약은 `MAJOR.MINOR`이며 값은 `boundary-contracts`가 정한다. 불변 산출물은 `ArtifactRef`(id, version, content_hash)로 가리킨다.

## 1. 목적과 범위

- 목적: 관리자가 문항을 추가·수정하고 검수받아, 게이트가 검사할 수 있는 불변 문항 버전으로 만든다.
- 하는 일: 저자가 올린 문항 자료(PDF 등 정해진 형식)를 파싱해 문항 초안으로 만들고, 저자가 사람이 읽는 미리보기로 확인하게 한다(D31). 저작 콘솔과 저작 API, 템플릿, 코드·단위 사전, 계약·의미 검증, 규칙 미리보기, 변경 영향 분석, 확인 워크플로, 문항 버전 관리, 개선 신호 수신.
- 저자: 문항을 올리는 사람은 의료인이며 신뢰한다. 컴퓨터 전문가가 아니므로 JSON·스키마·코드 목록을 직접 다루게 하지 않는다.
- 하지 않는 일: 임상 기준의 내용을 정하지 않는다(저자의 몫, D30). 모델 학습·평가, 릴리스 승인.

## 2. 소유하는 것

- 소유 저장소: 문항 저장소. 쓰기 창구는 저작 API 하나뿐이다.
- 제공하는 SDK 인터페이스: 문항 읽기 SDK(지정 버전의 `QuestionBank` 조회, 불변 버전 목록). 소비자는 합성 데이터, model-lab(D13), 게이트.
- 제공하는 서비스 API: 저작 API(문항 생성·수정·검수 제출). 관리자 콘솔 UI는 이 영역 안에 두되 저작 API의 클라이언트로만 구현해 나중에 분리할 수 있게 한다(D08).
- 이 SDK의 메모리 구현(가짜 구현)을 함께 배포한다.
- 생산하는 계약: `QuestionBank`(기존), `ReviewRecord`, `ChangeClassification`.

## 3. 소비하는 것

- 소비하는 계약: `QuestionBank`, `FailureCase`, `GateDecision`.
- 소비하는 SDK: 실패 사례 읽기 SDK(ops-feedback), 판정 조회(release-gate의 릴리스 읽기 SDK). 라이브러리로 turn-engine(규칙 미리보기), 문진 스키마.
- 지원하는 계약 버전: 문진 스키마 정수 버전, 경계 계약 `MAJOR.MINOR`.

## 3-1. 경계 명세 (블랙박스 기준)

상대 영역은 블랙박스다. 아래 인터페이스 번호의 시그니처, 오류, 멱등성은 `../boundary-contracts/INTERFACES.md`와 `CONVENTIONS.md`가 정한다. 이 명세 밖의 것을 상대에게 기대하거나 가정하지 않는다.

- 내는 것: **I1** QuestionReader(문항 세트 불변 버전, 검수, 변경 분류). 쓰기는 저작 API뿐.
- 받는 것: **I7**(개선 신호), **I4**(판정 조회), **I8**(규칙 미리보기).
- 해야 하는 것: 버전을 올릴 때마다 `ChangeClassification`을 만든다. 검수는 `ReviewRecord`로 남긴다. `QuestionBank` 스키마를 통과한 것만 저장한다. `reviewed_only` 조회에는 APPROVED이면서 `clinical_basis_approved`가 true인 버전만 나온다.

## 4. 상위 수용 기준

- 문항 버전은 불변이다. 수정은 새 버전을 만든다.
- 검수 기록이 없는 문항 버전은 게이트 후보로 노출되지 않는다.
- 모든 문항 버전은 `QuestionBank` 스키마를 통과한 것만 저장된다.
- 변경마다 `ChangeClassification`이 생성되고, 영향받는 슬롯과 필요한 후속 작업이 적힌다.
- 관리자 콘솔이 저작 API 외의 경로로 저장소에 쓰지 않는다.
- 파싱 결과는 저자가 미리보기로 확인하기 전에는 문항 세트 버전이 되지 않는다. 확인은 `ReviewRecord`(`reviewer_role`=저자 역할, `clinical_basis_approved`=true)로 남고 정확한 버전에 묶인다(D30).
- 형식은 추출기 단위로 추가할 수 있어야 한다. 어떤 형식이든 같은 미리보기와 저자 확인을 거친다. 파싱할 수 없거나 확신하지 못하면 추정하지 말고 알린 뒤 화면 입력(템플릿 양식)으로 이어 가게 해, 등록이 항상 가능해야 한다(D33).
- 원본 자료의 해시를 문항 세트 버전의 출처로 남긴다(`ext.question-authoring`에 기록, 계약 변경 없음).
- 파싱이 확신하지 못한 항목(수치, 단위, 범위, 위험 기준)은 미리보기에서 눈에 띄게 표시해 저자가 직접 확인하게 한다. 조용히 추정해 채우지 않는다.

## 5. 비기능 요구

- 지연·가용성: 미정. 학습·운영 서버와 달리 사용자가 관리자뿐이므로 영역이 제안한다.
- 자원: 일반 CPU 서비스.
- 보안·개인정보: 저자 인증·권한은 영역이 설계하되 경계에 닿으면 변경 요청을 낸다. 업로드된 문항 자료에 환자 정보는 없다고 가정하되 저장 전 경고한다.

## 6. 건드리면 안 되는 경계

- 문항 저장소에 쓰는 영역은 이 영역뿐이고, 쓰기는 저작 API로만 한다.
- 서비스의 Question Bank를 직접 갱신하지 않는다. 게이트를 거친 릴리스 묶음이 전달한다.

## 7. 이 영역에 해당하는 열린 결정

- O05 문항 변경 분류 기준: 확정: 문구 / 선택지·단위 / 슬롯 / 분기의 4종(D17).
- O12(D30), O15(D31): 닫힘.
- O18(D33): 닫힘. 지원 형식은 정해져 있지 않다. 요구는 저자가 가져온 문항을 등록할 수 있는 것이다. 어떤 형식을 먼저 지원할지는 영역이 정한다.
- 파싱 방식(규칙 기반, 모델 사용 등)은 영역이 정하되, 틀린 파싱이 임상 의미를 바꾸지 않도록 위 확인 절차를 지킨다.

## 8. 시드

저작 콘솔, 템플릿, 코드·단위 사전, 초안 변환기, 계약·의미 검증기, 규칙 미리보기, 변경 영향 분석기, 검수 워크플로, 문항 버전 관리자, 개선 신호 수신함.
